# Knowledge Base Schema

## Why the data is split this way

The CSV and JSON files are the source files. They are easy to update by hand when a listing changes. The application loads that data into PostgreSQL so the live app can query it quickly and consistently.

This matters because the app needs exact filtering for things like price, bedrooms, city, and availability. The text and brochure data still works well in a document-based retrieval layer when the user asks natural-language questions.

## Source tables and files

### properties.csv
This is the main property inventory.

### developers.csv
Developer profile data and project associations.

### locations.csv
City and area metadata.

### amenities.csv
Property-to-amenity links.

### schools.csv
Nearby school data by area.

### hospitals.csv
Nearby hospital data by area.

### payment_plans.csv
Structured financing and payment plan data.

### faqs.json
Frequently asked questions and the answers to them.

## Retrieval tables

The document chunks table is generated by the retrieval pipeline. It stores text chunks with embeddings so the app can do semantic matching on brochures, developer profiles, and FAQs.

## Notes

The first few property IDs are kept stable because the evaluation files reference them directly. This keeps the test set consistent as the rest of the project evolves.
